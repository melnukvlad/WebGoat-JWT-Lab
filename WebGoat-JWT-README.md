> **Навчальний практичний звіт** · Kali Linux + VirtualBox + Docker + WebGoat / WebWolf

## 1. Мета та завдання роботи

**Мета:** отримати практичні навички розгортання ізольованого середовища для тестування вебзастосунків, дослідити будову JSON Web Token (JWT), виявити ризики неправильного використання JWT та перевірки електронного підпису, а також сформулювати способи захисту.

Для досягнення мети поставлено такі завдання:

1. Розгорнути Kali Linux у віртуальній машині Oracle VirtualBox на комп'ютері з Windows 11.
2. Установити Docker всередині Kali Linux та запустити OWASP WebGoat **у контейнері**.
3. Перевірити доступність WebGoat і допоміжного застосунку WebWolf.
4. Розібрати формат JWT, алгоритми підписування та перевірки.
5. Виконати практичні вправи модуля `JWT tokens`, зафіксувати результати і проаналізувати причини вразливостей.

> **Обмеження середовища:** усі перевірки виконані лише на локальному спеціально вразливому навчальному застосунку OWASP WebGoat. Порти контейнера прив'язані до `127.0.0.1` усередині гостьової Kali Linux. Результати не стосуються сторонніх вебсервісів.

## 4. Теоретичні відомості

### 4.1. Призначення та структура JWT

**JSON Web Token** — компактний формат передавання набору тверджень (*claims*) між сторонами. Підписані JWT часто застосовують в системах автентифікації та авторизації. JWT **не обов'язково зашифрований**: у звичайному підписаному JWT вміст можна декодувати без знання ключа, але змінений вміст повинен бути відхилений під час перевірки підпису.

Типова форма підписаного JWT:

```text
BASE64URL(header).BASE64URL(payload).BASE64URL(signature)
```

| Частина | Зміст |
|---|---|
| **Header** | Метадані, зокрема алгоритм `alg` і тип токена `typ` |
| **Payload** | Твердження: ім'я користувача, права, термін дії тощо |
| **Signature** | Криптографічний результат, за яким перевіряють цілісність і автентичність підписаних даних |

![Структура JWT](screenshots/07-jwt-structure.png)

Під час вивчення теоретичних сторінок розглянуто: підміну поля ролі, зміну `user_id`, неправомірну зміну `exp`, повторне використання токена (*replay*) та маніпуляції з параметрами заголовка, зокрема `alg` і `kid`.

## 5. Практична частина: модуль `JWT tokens`

### 5.1. Завдання № 4 — `Decoding a JWT token`

**Мета:** декодувати переданий JWT та визначити користувача за його claims.

**Хід виконання:**

1. Відкрито четверту сторінку модуля JWT у WebGoat.
2. Скопійовано навчальний токен із поля `Given the following token`.
3. У WebWolf відкрито `JWT` і токен вставлено в поле `Encoded`.
4. Інструмент автоматично декодував частини `Header` і `Payload`.
5. У `Payload` знайдено поле `user_name`, що містило значення **`user`**.
6. На сторінці завдання у WebGoat введено `user` в поле `Username` і натиснуто `Submit`.

**Отриманий результат:** застосунок повідомив `Congratulations. You have successfully completed the assignment.` Сторінка № 4 стала зеленою.

Приклад декодованих навчальних даних:

```json
{
  "alg": "HS256"
}
```

```json
{
  "authorities": ["ROLE_ADMIN", "ROLE_USER"],
  "client_id": "my-client-with-secret",
  "scope": ["read", "write"],
  "user_name": "user"
}
```

*Примітка: показано лише частину claims, потрібну для пояснення. Повний токен не публікується.*

### 5.2. Завдання № 6 — `JWT signing`

**Мета:** у навчальному застосунку продемонструвати небезпеку довіри до алгоритму підпису, зазначеного в неперевіреному заголовку JWT, та до змінених прав користувача.

**Хід виконання:**

1. Відкрито сторінку № 6 `JWT signing` із формою голосування.
2. Через меню користувачів обрано тестового користувача **Tom**.
3. У Firefox відкрито **Developer Tools → Network**, виконано дію голосування та знайдено запит `POST .../votings`.
4. У запиті знайдено cookie `access_token` з навчальним JWT. Для ознайомлення зі структурою токен скопійовано в локальний WebWolf JWT Decoder.
5. Декодований заголовок містив `alg: "HS512"`, а `Payload` — `admin: "false"` та `user: "Tom"`.
6. У WebWolf у рамках вправи змінено значення `admin` на рядок `"true"` та алгоритм заголовка на `"None"`. Поле `iat` і ім'я користувача збережено.
7. Сформовано токен без підпису з формою **`header.payload.`** (третя частина порожня).
8. У Firefox через **Developer Tools → Storage** замінено значення тестової cookie `access_token` на підготовлений навчальний токен.
9. Без оновлення сторінки натиснуто значок очищення голосів.

Значення ключових полів **до модифікації**:

```json
{
  "alg": "HS512"
}
```

```json
{
  "admin": "false",
  "user": "Tom"
}
```

**Після модифікації в межах вправи:**

```json
{
  "alg": "None"
}
```

```json
{
  "admin": "true",
  "user": "Tom"
}
```

> У навчальному прикладі WebGoat було введено `"None"`. У специфікації JWS назва алгоритму без цифрового підпису записується як `"none"` (у нижньому регістрі). Це приклад некоректної конфігурації перевірки, а не безпечний спосіб авторизації.

**Отриманий результат:** голоси було скинуто; WebGoat вивів повідомлення `Congratulations. You have successfully completed the assignment.` Сторінка № 6 стала зеленою.

**Отриманий результат:** обидві обрані відповіді позначено правильними; WebGoat повідомив `Congratulations. You have successfully completed the assignment.` Сторінка № 8 стала зеленою.

У першому варіанті коду використано перевірку підписаного JWS за допомогою:

```java
Jwts.parser().setSigningKey(JWT_PASSWORD).parseClaimsJws(accessToken);
```

У наступному навчальному прикладі розглянуто менш суворий метод:

```java
Jwts.parser().setSigningKey(JWT_PASSWORD).parse(accessToken);
```

**Пояснення:** метод, що вимагає коректного підписаного JWS, відхиляє навчальний непідписаний токен. Загальний метод парсингу в старих або неправильно використаних реалізаціях може допускати обробку даних, яким не слід довіряти. Навчальні відповіді описують задум уроку; у реальному Java-коді фактична поведінка також залежить від версії бібліотеки й типів claims.

## 7. Рекомендації щодо захисту JWT

1. **Перевіряти цифровий підпис** кожного JWT до використання claims для автентифікації або авторизації.
2. **Фіксувати дозволені алгоритми на сервері**; не дозволяти токену самостійно диктувати алгоритм перевірки.
3. **Відхиляти непідписані токени** там, де політика застосунку вимагає підписані JWT.
4. Перевіряти `exp`, `nbf`, `iss`, `aud` та інші застосовні claims відповідно до контексту.
5. Не передавати конфіденційну інформацію у звичайному незашифрованому `Payload`.
6. Не покладатися лише на заявлену роль користувача без надійної перевірки походження токена й актуальних правил доступу.
7. Застосовувати актуальні бібліотеки перевірки JWT і тести на підміну алгоритму та claims.

У завданні № 6 на практиці продемонстровано ризик прийняття токена без належної перевірки підпису, що дозволило змінити `admin` та виконати адміністративну дію в навчальному застосунку. У завданні № 8 проаналізовано різницю між обробкою підписаного JWT та загальним парсингом токена; обидві відповіді успішно перевірено системою WebGoat.

**Головний висновок:** декодування токена не гарантує його справжності, а довіра до неперевірених claims створює ризик підвищення привілеїв. Контроль дозволених алгоритмів, перевірка цифрового підпису й коректна авторизація є необхідними умовами безпечного застосування JWT.

**Роботу ще не завершено повністю:** наступні практичні завдання модуля (сторінки 10–19) залишаються для подальшого проходження й документування.
